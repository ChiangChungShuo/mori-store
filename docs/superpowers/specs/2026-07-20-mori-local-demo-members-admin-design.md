# mori 本機完整商城示範設計

日期：2026-07-20

## 目標

在沒有 Supabase 憑證的本機環境，讓 mori 可以完整展示以下流程：

1. 顧客瀏覽多款 0–12 歲童裝並加入購物車。
2. 顧客以加減按鈕調整商品數量，畫面同步更新小計、運費與總額。
3. 顧客可註冊、登入、結帳並完成測試付款。
4. 顧客可查看自己的訂單。
5. 老闆可用預設管理員帳號登入，查看新成立的訂單與訂單內容。

正式環境維持既有 Supabase 驗證、資料庫與權限機制。本機示範功能僅在非正式環境且 `MORI_E2E_FIXTURES=1` 時啟用。

## 本輪範圍

### 商品目錄

- 將本機示範商品由 1 款增加至約 8 款。
- 商品涵蓋上衣、褲裝、洋裝、外套與幼兒服。
- 每款商品包含名稱、說明、年齡層、材質、洗滌方式、尺寸說明、圖片、價格、尺寸、顏色與庫存。
- 年齡篩選覆蓋 `0-2`、`3-5`、`6-9`、`10-12`。
- 商品圖片採一致的 mori 自然童裝攝影方向，避免所有商品共用同一張圖片。
- 本輪只增加本機展示資料，不改變正式 Supabase 商品資料與老闆上架流程。

### 購物車數量操作

- 每個商品列顯示減少按鈕、目前數量與增加按鈕。
- 增加按鈕每次增加 1，最高不超過商品庫存與系統單品上限 99。
- 減少按鈕每次減少 1，數量為 1 時停用；刪除商品仍使用獨立移除按鈕。
- 每次調整後即時更新商品小計、購物車件數、免運進度、運費與總額。
- 停用、滑過、鍵盤焦點與按下狀態必須清楚可辨識。
- 桌機與 375px 手機寬度不得出現橫向溢出。

### 會員登入與註冊

- 登入與註冊使用同一套 mori 會員視覺，包含品牌說明、表單卡片與清楚的頁面切換。
- 欄位包含 Email 與至少 8 個字元的密碼。
- 密碼欄提供顯示／隱藏控制。
- 顯示欄位錯誤、登入錯誤、註冊成功與處理中狀態。
- 本機註冊後建立一般會員帳號；會員可以使用相同帳密登入。
- 本機會員登入後前往原本要求的安全 `next` 路徑，沒有指定時前往 `/account`。
- 正式環境繼續使用 Supabase 註冊、Email 驗證與登入。

### 本機老闆帳號

- Email：`admin@mori.tw`
- 密碼：`mori123456`
- 只在本機示範模式有效。
- 登入成功後前往 `/admin`。
- 管理員狀態由伺服器端隨機工作階段識別碼與 HttpOnly Cookie 維護，不把密碼或角色放入瀏覽器可修改的儲存空間。
- 正式環境不接受此示範帳號，仍由 Supabase `profiles.role = admin` 判斷權限。

### 老闆訂單後台

- `/admin` 顯示今日訂單、待處理訂單與低庫存規格摘要。
- `/admin/orders` 顯示訂單編號、收件人、Email、金額、狀態與成立時間。
- 可依關鍵字與訂單狀態篩選。
- 點選訂單可查看商品、數量、收件資訊、7-ELEVEN／全家門市、金額及付款狀態。
- 未登入使用者前往管理頁時導向登入頁；一般會員不可查看管理頁。
- 本機完成測試付款後，訂單立即出現在管理員訂單列表。
- 本機示範訂單與新註冊帳號保存在開發伺服器記憶體；重新啟動伺服器後會回復種子資料。登入頁需明確提示此限制。

## 架構

### 環境路由

建立單一示範模式判斷，供商品、驗證、結帳、會員訂單與管理後台共用：

- 非正式環境且 `MORI_E2E_FIXTURES=1`：使用本機 fixture repository。
- 其他環境：使用既有 Supabase repository。

正式與示範 repository 實作相同用途的介面，頁面與元件不直接判斷資料來源。

### 本機共享狀態

以 `globalThis` 保存單一 fixture store，內容包含：

- 商品與規格。
- 一般會員帳號。
- 不透明工作階段識別碼與對應角色。
- 付款交易與已完成訂單。

結帳 repository 與管理訂單 repository 必須讀寫同一份 fixture store，確保顧客付款完成後老闆能立即看見訂單。fixture store 提供固定種子訂單，讓後台第一次開啟就有可辨識的畫面。

### 驗證邊界

- 本機 Cookie 使用 HttpOnly、SameSite=Lax、Path=/。
- 工作階段識別碼由伺服器隨機產生。
- 登入與註冊仍執行 Email、密碼及安全 `next` 路徑驗證。
- 管理頁只接受 fixture store 中角色為 `admin` 的有效工作階段。
- 所有示範分支在 production 關閉，避免示範帳密成為正式後門。

## 視覺設計

### 方向

延續 mori 的森林綠、米白與自然選品感。登入頁不再是散落在空白頁面的原始表單，而是「品牌敘事區＋會員表單卡」的雙欄版面；手機版改為單欄，先顯示表單。

### 元件

- 表單卡：清楚標題、補充文字、完整寬度欄位、主要動作與替代入口。
- 密碼控制：放在輸入框內側，文字使用「顯示／隱藏」。
- 管理後台：使用較緊密的資訊密度、狀態標籤與可橫向捲動的表格容器；手機版以訂單卡片呈現重要資訊。
- 數量步進器：保持無圓角的選品店風格，增加明確的 hover、focus-visible、active 與 disabled 狀態。
- 獨特元素：會員頁以細線尺寸刻度與 0–12 歲年齡文字作為品牌識別，不加入無意義裝飾動畫。

## 資料流程

### 顧客

商品頁 → 加入購物車 → 調整數量 → 登入或訪客結帳 → 選擇超商門市 → 測試付款 → 建立訂單 → 清空購物車 → 訂單完成頁。

### 老闆

登入頁輸入本機管理員帳密 → 建立 HttpOnly 工作階段 → `/admin` → `/admin/orders` → 查看訂單明細。

## 錯誤與空狀態

- 登入失敗明確顯示「Email 或密碼不正確」。
- 重複註冊顯示帳號已存在。
- 工作階段失效時導回登入並保留安全的返回路徑。
- 訂單列表沒有資料時說明如何建立第一筆測試訂單。
- 商品達庫存上限時停用增加按鈕，不讓數量短暫超出後再回復。
- 伺服器重新啟動造成示範資料重置時，不顯示資料遺失錯誤；頁面以固定種子資料重新開始。

## 測試與驗收

依測試驅動方式逐項實作：

1. 商品 fixture 測試：多款商品、篩選、商品明細及購物車刷新。
2. 購物車測試：增加、減少、庫存上限、金額與免運進度更新。
3. 驗證測試：註冊、登入、錯誤帳密、管理員角色、登出與安全返回路徑。
4. 管理訂單測試：新付款訂單出現在列表、篩選與明細。
5. 瀏覽器流程：一般會員註冊登入、顧客付款、管理員登入查看同一筆訂單。
6. 介面驗收：登入、註冊、購物車及管理訂單頁在桌機與 375px 手機均無橫向溢出，鍵盤焦點清楚可見。
7. 完整執行 lint、單元／整合測試、Next.js build 與 Playwright 測試。

## 不在本輪範圍

- 正式綠界、藍新或其他第三方金流。
- 正式 Email 寄送、忘記密碼與 Email 驗證服務。
- 本機資料跨開發伺服器重啟持久保存。
- 變更正式 Supabase schema 或正式商品資料。
- 新增本機專用的商品上架與圖片上傳資料庫；正式商品上架頁維持既有 Supabase 流程。
